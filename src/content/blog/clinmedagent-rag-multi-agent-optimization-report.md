9 月写[《把教材变成可以解题的本地知识库》](/blog/把教材变成可以解题的本地知识库-一次医学rag实现记录/)时，我关心的是怎样把图片型教材变成能够检索、能够引用原书页码的证据层。后来，这个项目逐步补齐了文字层解析、OCR、表格结构化、本地网页、CLI、MCP 和 JSON Bridge，功能越来越完整，几个小范围里看不出来的成本也开始叠加。

这次我对 **ClinMedAgent-RAG 做了一轮多层协作审计与优化**。最终提交是 [`1069613`](https://github.com/AnAcretiondisk9986/ClinMedAgent-RAG/commit/1069613367fb16ba9c6ee7947a100b354094f495)：27 个文件，新增 2,653 行、删除 263 行，涵盖实现、回归测试和文档。

最直观的结果是：同一份 4 本教材、3,463 个文本块的索引上，10 个固定问题的平均搜索耗时从 **104.3 ms 降到 50.2 ms，下降约 51.9%**。更值得记录的，是这次怎样拆分测量、怎样限制修改，以及复核为什么发现了“修复本身带来的问题”。

![ClinMedAgent-RAG 搜索耗时对比：104.3 ms 降至 50.2 ms；44 条回归查询保持一致，测试由 249 项增加到 289 项](/images/clinmedagent-rag-optimization-20261117.svg)

## 一、先约定数字的含义

项目的处理链路可以简化成：

```text
教材 PDF
  ├─ 有文字层 → 直接提取
  └─ 图片页   → OCR / 版面 / 表格处理
                     ↓
           带原书页标的结构化 Markdown
                     ↓
         SQLite 正文表 + FTS5 二元组索引
                     ↓
          词法打分 → 有界候选 → 向量重排
                     ↓
              CLI / Web / MCP / Bridge
```

本轮默认向量后端仍是零依赖的词法二元组实现。这里的“向量重排”不意味着已经引入了通用语义模型，也不意味着系统能自行判断医学答案是否成立。

性能比较使用 Windows、Python 3.14.3 和 PyMuPDF 1.27.2.3 环境下的**本机索引副本**。每轮先执行一次预热查询，再顺序运行固定的 10 个问题，每题取前 5 条，重复三轮。报告中的 mean 是“各题三轮平均耗时”的算术平均。

| 指标 | 改前 | 改后 | 测量范围 |
| --- | ---: | ---: | --- |
| 平均搜索耗时 | 104.3 ms | 50.2 ms | `Library.search()`，不含连接创建和关闭 |
| 10 题中最慢一题的平均值 | 176.2 ms | 114.3 ms | 同一套查询，各题先取三轮平均 |
| 打开索引库耗时中位数 | 121.7 ms | 2.9 ms | 单独的开库探针，预热后重复打开 |
| 自动化测试 | 249 passed | 289 passed | 本轮记录的完整测试运行结果 |
| 检索回归样本 | — | 44 / 44 一致 | 每题最多前 8 条，比较结果标识与分数 |

这组数字有几个边界。它是暖缓存、小型本地书库的测量，没有压测数万块语料，也没有给出线上 p95；搜索计时在 `Library()` 之后开始，所以 **50.2 ms 不能直接当成网页请求的端到端延迟**；44 条回归查询一致，只能证明这组样本未漂移，不能证明所有输入的排名都完全等价。

原始汇总里还有一个统计小坑：脚本把排序后数组的上中位元素标为 median。10 个数的标准中位数应取中间两项平均，因此本文不沿用该脚本的搜索 median，只引用均值和最慢题均值。开库探针使用的是 `statistics.median()`，属于另一项测量。

## 二、协作怎样拆，决定了能否安全地合并

这轮审计分为三个层级：4 个域扫描角色覆盖检索内核、服务接口、前端工作台、流水线与诊断；8 个文件深挖角色把热点细化为带位置和验证方法的问题；4 个汇总角色去重、核实并整理成分域报告。随后由 4 个实施角色分别修改互不重叠的文件，再由 3 个复核角色做差异审查、边界探针和文档核对，最后补一轮硬化与主代理收尾。

这里的“多层”指任务的拆解与汇总层级。实际执行由主代理编排，并不能只凭角色数量就推断它比单代理更高效。

最有用的约束是**写入范围清晰、验收证据独立**。例如，检索组负责 `library.py / qa.py / rerank.py`，前端组负责网页静态资源；服务层与流水线组各有自己的文件和测试范围。审计阶段不改实现，实施阶段不越界碰别人的文件，最后统一运行全量测试。

审计记录收集到 61 条问题。这个数是整理任务的起点，不是 61 个独立故障：服务层与检索层会同时观察到“每请求开库”，多个风险条目也可能共享同一根因。实际取舍应看问题能否复现、修改是否有回归保护。

## 三、最大的固定成本藏在打开数据库时

最初看搜索大约需要 100 ms，直觉上容易继续调召回与排序。但把 `Library()` 的构造单独计时后，发现它还要额外付出一百多毫秒。

初始化做的事情都很合理：建表、补列、迁移路径、检查 FTS 与向量索引是否需要回填。问题是，这条路径最后还会无条件执行：

```python
self.cx.execute(f"PRAGMA user_version = {SCHEMA_VERSION}")
self.cx.commit()
```

即使版本已经是当前值，也把同一个版本号再写一次。新连接首次写数据库头并提交 WAL 的成本，让“只是打开看看”的操作变成了写者。服务层又在请求中频繁创建连接，开库成本便被用户反复承担。

修复保留了每条连接都需要设置的 `foreign_keys`，也保留迁移和回填检查；只是先读取版本，只有不同才写回，并在真的存在事务时提交：

```python
# 机制示意，省略建表、迁移和回填代码。
current_version = self.cx.execute("PRAGMA user_version").fetchone()[0]

if current_version != SCHEMA_VERSION:
    self.cx.execute(f"PRAGMA user_version = {SCHEMA_VERSION}")
if self.cx.in_transaction:
    self.cx.commit()
```

另外两笔成本也一起处理了。二元组索引计数从 FTS 虚表查询换成其 `_docsize` 影子表计数，并保留旧 SQL 回退；向量表增加 `backend` 索引，避免每次按后端计数都扫描整表。审计中的计时拆解显示，前者约从 27 ms 降到 0.1 ms。

最终开库探针的中位数从 **121.7 ms 降到 2.9 ms**。这是“已完成迁移、索引完整”的常规路径结果；新库、旧库迁移和缺索引回填仍然可能写盘，不能概括成“初始化从此没有写操作”。

## 四、搜索优化：把昂贵工作留给真正需要的候选

### 先确认命中，再构造全文特征

旧打分循环对每条候选都先构建全文二元组集合、规范化元数据，然后才检查有没有真正命中的概念。对最后会被 `continue` 丢掉的行，前面的工作全部浪费。

调整后，循环先做便宜的概念命中判断：

```python
matched = [term for term in tokens if term in text]
if not matched:
    continue

# 后续才计算全文二元组重叠、概念距离与标题信号。
```

同一 token 的 `text.count()` 结果用于多个评分项，原来会重复计算，这次也合并了。不过，一次看似自然的“用字典缓存词频”又引入了偏差：OCR 纠错和大小写规范化之后，两个概念可能变成相同的 token，字典会把它们合并。

例如 `DNA dna 复制` 就能触发这类情况。旧算法按列表中的出现次数累计贡献，换成字典后分数甚至首位结果都会变化。最后改为保留列表语义：

```python
counts = [(term, text.count(term)) for term in matched]
hits = sum(count for _, count in counts)
concept_boost = sum(min(count, 3) * 0.55 for _, count in counts)
```

如果要改变重复概念的权重，可以单独讨论；这轮性能优化先守住原有评分含义。

### 向量只给前 200 条候选取

另一个热点在 SQL 和 Python 之间。旧候选查询对所有召回行都 `LEFT JOIN chunk_vectors`，把向量序列化文本一起取回；但重排器只处理词法候选中的前 200 条。

两道较慢问题一次会带回约 1.76–2.01 MB 的向量文本，其中大部分用不上。修改后，候选查询先只取正文和评分所需元数据，完成词法打分与截断后，再按候选标识批量取向量。

```text
之前：召回全部候选和向量 → Python 打分 → 截断到 200 条
之后：召回正文与元数据 → Python 打分 → 截断到 200 条 → 取对应向量
```

这里没有给 FTS 召回直接加一个随意的 `LIMIT`。提前截断可能把后续 Python 评分认为最相关的候选扔掉。把重数据的读取推迟到既有的重排边界，风险更容易控制。

### 多遍问答也需要预算

`answer_question()` 会把完整题干、概念联合查询、单概念与选项查询合并。每增加一遍，就是再执行一次搜索。旧规划能生成六到八遍，其中单字查询还可能触发全表扫描。

这次把默认预算收敛到四遍，减少单字单独成遍，并给合并后的选项查询预留名额。单题探针中，“红、肿、热、痛”问题从六遍、约 1.3 秒，降到三遍、约 149 ms。它属于单题观察，不能替代完整问答基准。

**单字回退本身保留了。** 尝试只用混排查询中的多字概念预筛时，“骨的构造”可能只因正文包含“骨”而成为有效候选；拿“构造”当召回前提会丢页。已有测试拦住了这个改法，最后优化遍数和计算成本，保留召回语义。

## 五、只读降级必须连同检索语义一起设计

“跳过写入就能读”是这轮最容易误判的地方。

数据库可能已经有正文，却尚未回填二元组索引。如果只读介质上回填失败后直接跳过，初始化看似成功，中文查询却会在空索引上查出零行。探针里，“上皮组织”“细胞膜”“肩关节”都能这样静默失去召回，拉丁词还可能碰巧通过另一套 FTS 回退获得结果，让故障更难察觉。

因此降级分成两件事：记录 `readonly` 与可读的警告，阻止写操作继续执行；再判断二元组索引是否覆盖正文。如果不完整，就禁用 ngram 预筛，退回较慢的正文扫描。对现有结构仍可读取的库，这样才能保留尽力检索的含义。

诊断工具使用专门的只读连接。SQLite 的只读打开可能直到首次查询才暴露 WAL 访问问题，所以还需要哨兵查询；必要时尝试 `immutable=1`。但 immutable 会忽略锁与变化，适用前提应是确认数据库不会变化的快照，不能把它当作访问活跃数据库的万能替代。

另一个复核发现是：把读取异常一概降成 warning，会把真正损坏的数据库也判成“健康”。收尾加入只读可执行的 `PRAGMA quick_check`，把可见的页结构损坏作为错误报告。

这里仍有边界：`quick_check` 不等于 FTS 的完整语义校验，行数一致也不能证明所有倒排词条都正确；本轮只读测试以文件属性和已有受限环境为主，并没有覆盖每一种只读文件系统或历史 schema。

## 六、子进程超时之后，还有几个退出陷阱

OCR、版面分析和表格处理都是长耗时子进程。旧路径直接迭代 stdout，子进程没有输出、或派生进程仍握着管道时，主线程可能一直等不到 EOF，无法及时检查取消标记。

第一轮修改把 stdout 放到后台读线程，再通过队列把行交给主线程。主线程周期性检查取消和阶段截止时间，超时则终止进程并回收。

但“加了 timeout”不代表退出路径就安全了。独立复核追到了几个问题：

- **关闭 stdout 也能卡死。** 读线程阻塞在管道读取并持有缓冲锁时，主线程调用 `stdout.close()` 可能再次永久等待。最终把流的收尾交给读取线程，主线程只在正常 EOF 后补关。
- **POSIX 杀进程组前必须隔离进程组。** 如果创建子进程时没有 `start_new_session=True`，`killpg` 可能把服务自己也包含进去。代码补了独立会话；这条平台路径在本轮 Windows 环境中主要由代码复核确认，未做 Linux 端到端验证。
- **不要按过期 PID 取消上一阶段。** 阶段已经退出而任务仍保留其 `Popen` 引用时，Windows PID 存在复用风险。取消入口恢复存活检查，避免无条件按旧 PID 发起杀树。

Windows 的 `taskkill /T`、POSIX 进程组、daemon 读线程，都有各自的边界。父进程提前退出后怎样稳定回收全部后代，仍值得用 Job Object 或更明确的进程所有权机制补测。这次能够说明退出路径比原来更受控，不能声称所有 GPU worker 和孙进程场景都已经验证完毕。

## 七、本地工作台的安全与交互一起收敛

本地服务同样会被浏览器中的别的页面请求。服务端补了 Host 检查、Origin / Fetch Metadata 检查，以及 JSON 变更接口的媒体类型要求；远程监听仍依赖显式开启和访问令牌。超大 JSON 体返回 413，错误媒体类型返回 415，坏 JSON 或非对象体返回 400，MCP 遇到非法输入也会返回错误而不是直接退出。

这属于对已识别风险的加固，**不是一次完整的安全证明**。实际 Origin 实现比较端口，并允许部分回环别名和主机白名单；它还没有完整按“服务实际协议、规范化主机、端口”组成的三元组严格比较。通配绑定的 Host 校验也有不同分支，不能把本轮总结成“所有跨站与重绑定路径都已封死”。

连接复用也按线程所有权处理。`ThreadingHTTPServer` 的长连接能复用本线程的 `Library`，短连接则在 handler 收尾时释放。SQLite 默认连接不能由别的线程使用或关闭，所以跨线程收尾改成登记请求，由拥有连接的线程完成关闭，避免“账本清空、实际句柄仍然活着”。

前端这轮主要减少无效工作：翻页滑块做 150 ms 去抖，预览图宽度统一到五档；侧栏按渲染字段签名跳过无变化重建；异步详情返回时确认当前选中的书没有变化；请求增加超时和上传取消。还补齐了复制正文、原书页号、返回检索与结果计数，修正暗色主题和正文栏宽度。

服务端的预览缓存增加了按容量清理，但检查是周期触发，属于软上限。前端语法与静态断言通过，并不等于每个响应式尺寸都经过真实浏览器回归；本轮也没有重新跑完整 GPU OCR 流水线。

## 八、为什么测试全绿之后还要独立复核

原有完整测试是 249 passed，最后记录为 **289 passed、26 个 subtests**。新增测试覆盖了 HTTP 输入边界、只读数据库、跨线程回收、阶段超时、缓存失效和产物原子写等路径。

另有 44 条固定回归查询，每题最多比较前 8 条结果的标识与分数。最后逐题一致。这份集合很有用，但重复 token 的例子已经说明它不充分：**44 / 44 一致，仍然可能在第 45 种输入上改变排名。**

本轮的对抗探针补了普通测试没覆盖到的输入：引号和 NUL、超长查询、空值 limit、八线程调用、短连接与 keep-alive、后缀 Range、MCP 非法报文，以及需要迁移或回填的只读老库。

其中，FTS 的问题尤其容易和 SQL 注入混淆。SQL 参数绑定保护的是 SQL 语法层；绑定参数内部的 FTS `MATCH` 表达式仍有自己的语法。用户输入被切成二元组再拼进短语后，引号可能造成解析错误，也可能静默改变表达式含义。修复为过滤不适合构成短语的片段，并在 FTS 失败时回退正文扫描。

比较脚本自己也曾误报：把 overlap 的分母固定成 5，会让只返回两条结果、或两边都没有结果的查询永远无法“完全一致”。修正验证器、再核对逐条结果，是这轮验收的一部分。

## 九、最重要的未完成项：有命中，不等于足以作答

这次性能优化没有改变 `evidence_found` 的判定。它仍然主要取决于证据候选是否非空，不能直接理解成“教材已经支持问题中的结论”。

一组人工挑选的 32 个问题中，20 个被标为语料内，19 个返回候选；12 个被标为语料外，其中 **8 个也返回了候选**。有一个关于化疗后中性粒细胞减少的问题，首个结果甚至来自政治理论教材。这是明显的误匹配信号。

但这组样本还不构成正式的医学答案质量评测。“返回了候选”的 19 / 20 不能写成“回答准确率 95%”；语料外标签也需要逐题核对，教材提到某种疾病，并不意味着它包含所问的评分标准或治疗方案。

本轮先增加 `coverage`、`matched_concepts`、`subject_matched` 等可解释信号，没有贸然加一个固定分数阈值。原因很实际：正负样本的分数区间重叠，覆盖度也会被通用措辞和问题拆解方式影响。

下一步需要更可靠的人工标注集，分别判断“主体是否出现”“证据是否回答问题”“引用能否支持最终结论”。词在语料里的出现频次可以作为信号，但不能单独决定可答性。真正面向用户作答时，仍应核对原文，只展示书名、原书页码和章节；内部证据标识不该出现在普通医学答案中。证据不足时，要明确说明“本地教材未检索到依据”。

另外两项保留为后续工作：章前页的分章与入库缺口，需要在索引副本上改完逻辑并重新验证；`outputs._commit` 的逆序落盘设想涉及故障回滚测试，本轮曾尝试但最终撤回。文档中列出的建议，不应算作已经完成的实现。

## 十、复现与后续工作

这次最关键的经验是，把**初始化、召回、评分、重排和问答规划分开计时**。否则会把固定开库成本当成搜索算法问题，也会把单题问答的提速混进单遍搜索指标。

下面是一个只读索引副本上的搜索计时示例，方便检查自己的问题集；它不重建本轮原始基准，也不包括开库耗时：

```python
from pathlib import Path
from statistics import mean
from time import perf_counter
from medical_rag.library import Library

# 请换成自己的索引副本与教材根目录。
lib = Library(db=Path("bench-copy/library.sqlite3"), root=Path("workspace"))
questions = ["肱骨的形态特点", "肝小叶的结构", "DNA 复制的过程"]

try:
    lib.search(questions[0], limit=5)  # 预热
    for question in questions:
        samples = []
        for _ in range(3):
            started = perf_counter()
            lib.search(question, limit=5)
            samples.append((perf_counter() - started) * 1000)
        print(question, round(mean(samples), 2), "ms")
finally:
    lib.close()
```

要重做前后比较，需要在同一环境、同一索引副本上分别使用父提交与本次提交，固定预热方式、查询顺序、结果条数和向量后端。原始本机基准脚本、探针和索引副本属于未入库的过程产物，公开仓库里不能直接照抄路径就得到同一份数据；本文保留聚合数字和方法，不发布教材正文与个人机器路径。
